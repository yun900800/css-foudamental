# CSS 结构设计八原则

> 从 Jen Simmons vs Gemini 实现对比中提炼的结构设计框架
> 核心思想：**先理清元素之间的关系，再决定布局系统。结构对了，代码自然会简单。**

---

## 原则一：关系分类 —— 包含 vs 平等（⭐ 入口原则）

这是所有结构设计的**第一个决策**，决定整个架构走向。

### 两种关系类型

| 关系类型 | 定义 | 例子 |
|---------|------|------|
| **包含关系**（父子/嵌套） | 一个元素从属于另一个元素 | 按钮在卡片内、列表项在列表中 |
| **平等关系**（兄弟/并列） | 元素之间对话，各自独立 | 图片 vs 标题、标题 vs 版权信息 |

### 判断工具：删除测试法

> **如果我要把这个元素从页面中删除，其他元素会跟着移动吗？**

| 场景 | 判断 | 关系类型 | 结构建议 |
|------|------|----------|----------|
| 删除版权文字，标题会动吗？ | **不会** | **平等关系** | 不该和标题装在同一个容器里 |
| 删除标题中的 "Twopots"，"Design" 会移动吗？ | **会**（在同一行） | **包含关系** | 用 span 嵌套在标题内合理 |
| 删除图片，标题的位置需要变吗？ | **不需要**（grid 已定义） | **平等关系** | 同级 grid item |
| 删除卡片，卡片内的按钮会消失吗？ | **会** | **包含关系** | 按钮放在卡片内部 |

### 两种错误倾向

**错误一：把平等关系嵌套成包含关系**

```html
<!-- ❌ 标题和版权信息是平等关系，却被装在一起 -->
<div class="typography-group">
    <div class="brand-title">Twopots Design Studio</div>
    <footer class="meta-footer">Barcelona</footer>
</div>
```

后果：需要用 `position: absolute` 弥补结构错误，脱离文档流 → 响应式需重新计算坐标。

**错误二：把包含关系拆成平等关系**

```html
<!-- ❌ 标题中的三个词应该属于同一个标题 -->
<span>Twopots</span>
<span>—— Design</span>
<span>Studio</span>
```

后果：三者之间缺少统一的结构约束，需要用 `translateX` / `margin` hack 对齐。

### 结构决策

- **平等关系 → 放进同一个 grid / flex 上下文**，共享空间坐标系
- **包含关系 → 直接嵌套**，父容器定义边界，子元素填充内部

## 原则二：源顺序即语义优先级

> **HTML 中的顺序应该反映内容的逻辑优先级，而非视觉位置。**

```html
<!-- ✅ 正确：main 在前因为它是主要内容 -->
<main>
    <h1>主标题</h1>
    <p>正文</p>
</main>
<aside class="sidebar">...</aside>
```

### 为什么重要

- 屏幕阅读器按源顺序读
- 打印样式、窄屏重排都依赖源顺序
- CSS Grid / Flex 可以通过 `order` / `grid-area` 在视觉上重新排列

### 案例对照

| 实现 | 源顺序 | 分析 |
|------|--------|------|
| **Jen Simmons** | `img → h1 → ul` | 图片是视觉主体 → 大标题 → 附属信息，符合内容优先级 |
| **Gemini** | `graphic-wrapper → typography-group → meta-footer` | 按视觉分组而非语义优先级，嵌套深且结构模糊 |

## 原则三：从外向内设计（Outside-In）

> **先定大关系，再定内部关系。不要跳层。**

```
第一步：页面 → 确定大区域划分
┌─────────────────────────────┐
│         header              │
├─────────────────────────────┤
│         main                │
├─────────────────────────────┤
│         footer              │
└─────────────────────────────┘

第二步：header 内部 → 确定子元素关系
┌─────────────────────────────┐
│  图片   ← peer →  标题      │
│                   版权      │
└─────────────────────────────┘

第三步：标题内部 → 确定词之间的排列
┌─────────────────────────────┐
│  T  │  D  │  S  │
│  w  │  e  │  t  │
│  ...                      │
└─────────────────────────────┘
```

**每层只关注当前层的关系**，不跳层思考。Gemini 的嵌套问题就是从第一步直接跳到了第三步——试图同时在所有层级上解决问题。

## 原则四：一个容器一个职责

> **每个 Grid / Flex 上下文只能负责一件事。**

```css
/* ❌ 混淆：一个容器同时管大布局、文字样式、装饰效果 */
.poster {
    display: grid;
    grid-template-columns: 1fr 2fr;
    font-size: clamp(...);
    filter: drop-shadow(...);
}

/* ✅ 清晰：每层分工明确 */
header {
    display: grid;
    grid-template-columns: 1fr min-content min-content max-content 100px;
    /* 职责：仅管理大布局关系 */
}

h1 span {
    writing-mode: vertical-rl;
    font-size: 3rem;
    /* 职责：仅管理文字方向与大小 */
}
```

### 检查标准

如果同一个选择器里同时包含：
- **布局属性**（`display` / `grid-*` / `position` / `flex-*`）
- **装饰属性**（`background` / `filter` / `box-shadow` / `font-*`）

考虑拆分。

## 原则五：网格不要穿层

> **每一层只和它的直接子元素打交道。**

```css
/* ❌ 越级：header 的 grid 直接决定了 span 的排列 */
header { display: grid; }
header span { ... }      /* header 的直接子元素是 h1，不是 span */

/* ✅ 分层：每层管好自己的直接子项 */
header { display: grid; }           /* 管 header 的直接子项 */
header h1 {
    grid-row: 2;                    /* h1 是 header grid 的直接子项 */
    grid-column: 2 / 4;
}
h1 {
    display: grid;                  /* h1 自己管自己的直接子项 */
    grid-template-columns: repeat(3, 0.9em);
}
h1 span {
    writing-mode: vertical-rl;      /* span 是 h1 grid 的直接子项 */
}
```

**穿层管理的出现，往往是"关系分类"错误或"嵌套过深"的信号。**

## 原则六：视觉顺序 ≠ 结构顺序

> **利用 Grid / Flex 的视觉重排能力，保持源顺序语义化，视觉上重新排列。**

结构服务于**意义**，CSS 服务于**视觉**。这两者可以分离。

```css
header {
    display: grid;
    grid-template-columns: 1fr min-content min-content max-content 100px;
    grid-template-rows: 700px auto auto;
}

img {                  /* 第一个子元素，语义上是最重要的视觉主体 */
    grid-column: 1 / -1;
    grid-row: 1 / -1;
    justify-self: end; /* 视觉上推到右侧 */
}

h1 {                   /* 第二个子元素，语义上是品牌名称 */
    grid-row: 2;
    grid-column: 2 / 4;  /* 视觉上在图片右下 */
}

ul {                   /* 第三个子元素，语义上是附属信息 */
    grid-row: 3;
    grid-column: 3 / 5;  /* 视觉上在最底层右侧 */
}
```

语义顺序是 `img → h1 → ul`，但利用 grid 可以让它们视觉上任意分布。这就是**结构独立于视觉的力量**。

## 原则七：最少容器原则

> **每增加一个容器 wrapper，都要付出结构复杂度、阅读成本、调试成本的代价。**

### 要不要加这个 wrapper？

| 理由 | 是否合理 |
|------|---------|
| 为了语义分组（如 `<header>`） | ✅ 合理 |
| 为了创建新的布局上下文（h1 包 span） | ✅ 合理 |
| 为了单独控制背景/间距 | ✅ 合理 |
| "感觉应该包一层" | ❌ 不必要 |
| "为了绝对定位找个锚点" | ⚠️ 警示信号 |
| "别人都是这么做的" | ❌ 独立思考 |

### 案例对照

| 实现 | 容器数 | 分析 |
|------|--------|------|
| **Jen Simmons** | 1 个 `<header>` | 零多余容器，所有主要元素是直接子项 |
| **Gemini** | 4 层: `art-stage` → `graphic-wrapper` / `typography-group` → `brand-title` / `meta-footer` | 有多层冗余容器，`graphic-wrapper` 纯粹为了包裹 `<img>` |

## 原则八：可预测的溢出

> **结构设计时，想清楚"如果这里的内容变长了会怎样？"**

### 要问自己的问题

- **文字变长** → 用 `overflow: hidden` 还是允许换行？
- **图片比例不同** → 用 `object-fit` 裁剪还是保持比例？
- **翻译成其他语言** → 不同语言的单词长度差异很大
- **用户缩放字体** → 布局会崩吗？

### Jen 的示范

```css
grid-template-columns: 1fr min-content min-content max-content 100px;
```

- `min-content` → 文字可以收缩到最短宽度
- `max-content` → 文字不被截断时保持完整
- `1fr` → 吸收剩余空间，保持整体平衡
- `100px` → 固定的右侧呼吸空间

**每一种轨道单位都在说"如果内容变了"的答案。**

## 完整的结构设计流程

```
Step 1: 关系分类（原则一）
        ↓
Step 2: 从外向内逐层设计（原则三）
        ↓
Step 3: 确保每个容器只有一个职责（原则四）
        ↓
Step 4: 确认源顺序反映语义而非视觉（原则二 + 六）
        ↓
Step 5: 检查有没有多余 wrapper（原则七）
        ↓
Step 6: 检查是否存在穿层管理（原则五）
        ↓
Step 7: 考虑内容溢出的各种可能性（原则八）
```

## 检查清单（快速自查）

写代码前/重构时逐条打勾：

- [ ] 元素之间是**包含关系**还是**平等关系**？用删除测试法验证
- [ ] 结构是否**从外向内**设计？没有跳层？
- [ ] 每个容器的职责是否**单一明确**？
- [ ] 源顺序是否反映**内容优先级**而非视觉位置？
- [ ] 是否充分利用了 Grid/Flex 的**视觉重排**能力？
- [ ] 有没有多余的 wrapper 可以去掉？
- [ ] 有没有穿层管理的情况？
- [ ] 内容变化（溢出/翻译/缩放）时，布局还稳定吗？
